# Querying Data with SELECT in SQL

#### TL;DR (Quick Revision)

**`SELECT` Statement** = Retrieve specific columns (`SELECT col1, col2`), all columns (`SELECT *`), computed expressions, or grouped summaries (`GROUP BY ... HAVING`) + Evaluated in strict **Logical Query Execution Order (`FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> DISTINCT -> ORDER BY -> LIMIT/FETCH`)**.

> [!abstract] Core Idea
> The **`SELECT` statement** is the core workhorse of Data Query Language (`DQL`), allowing you to retrieve specific columns, calculate new expression columns, sort result sets, group rows into summary buckets, and filter those groups ([SELECT Transact-SQL](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-transact-sql?view=sql-server-ver17) & [What is SQL? - ApX Machine Learning](https://apxml.com/courses/sql-for-data-science/chapter-1-intro-databases-sql/what-is-sql)). Even though `SELECT` is the **first** word you type, the database engine evaluates `SELECT` at **Step 5**—after `FROM` (Step 1), `WHERE` (Step 2), `GROUP BY` (Step 3), and `HAVING` (Step 4)!

> [!question] Why Use It?
>
> - **Retrieve Only the Columns You Need (`SELECT col1, col2`)**: Avoids reading heavy unused columns from disk and allows the database to satisfy queries directly from a slim **Covering Index** ([SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)).
> - **Compute Derived Metrics on the Fly**: Calculate `ytd_sales - monthly_quota AS quota_surplus` directly inside `SELECT` without altering stored table data.
> - **Summarize Rows into Regional/Departmental Buckets (`GROUP BY`)**: Collapse detail rows into summary rows with `COUNT()`, `SUM()`, `AVG()`, `MIN()`, and `MAX()` ([Using MIN and MAX Functions in SQL](https://apxml.com/courses/sql-for-data-science/chapter-4-aggregating-data/finding-min-max)).
> - **Filter Groups Based on Aggregate Rules (`HAVING`)**: Keep only regions or categories that meet group-level thresholds (`HAVING COUNT(*) >= 2`).

## The Learning Concept

### What Problem Does It Solve?

Because SQL is written starting with `SELECT`, beginners naturally assume `SELECT` runs first and try to use a `SELECT` column alias inside `WHERE`, or put aggregate functions like `SUM()` inside `WHERE`:

```sql
-- BAD - Referencing a SELECT alias in WHERE, and putting an aggregate function in WHERE
SELECT
    region_name,
    ytd_sales - monthly_quota AS quota_surplus
FROM sales_reps
WHERE quota_surplus > 10000.00        -- ERROR: 'quota_surplus' does not exist yet when WHERE runs (Step 2)!
  AND SUM(ytd_sales) > 100000.00;     -- ERROR: Aggregate functions cannot appear in WHERE!
```

When the database executes a query, `FROM` runs at Step 1 and `WHERE` runs at Step 2—long before `SELECT` creates the alias `quota_surplus` at Step 5! Likewise, groups are not formed until `GROUP BY` (Step 3), so aggregate filters belong in `HAVING` (Step 4). Here is the clean solution that respects SQL's execution order:

```sql
-- GOOD - Repeat the expression in WHERE (Step 2) or filter aggregates in HAVING (Step 4)
SELECT
    region_name,
    COUNT(*) AS rep_count,
    SUM(ytd_sales) AS regional_sales
FROM sales_reps
WHERE (ytd_sales - monthly_quota) > 0.00  -- Step 2: Filter individual rows BEFORE grouping
GROUP BY region_name                      -- Step 3: Bucket remaining rows by region_name
HAVING SUM(ytd_sales) > 100000.00         -- Step 4: Filter the grouped buckets
ORDER BY regional_sales DESC;             -- Step 7: Sort using the SELECT alias created in Step 5!
```

### How SQL Implements It

> [!tip] The 8-Step Logical Query Execution Pipeline
>
> 1. **`FROM` (and `JOIN`)**: Locate the source table(s) and build the initial virtual working set.
> 2. **`WHERE`**: Filter individual rows; only rows where the condition is `TRUE` survive.
> 3. **`GROUP BY`**: Bucket the surviving rows into groups based on shared column values.
> 4. **`HAVING`**: Filter the grouped buckets using aggregate conditions (`COUNT`, `SUM`, `AVG`).
> 5. **`SELECT`**: Evaluate expressions (`ytd_sales - monthly_quota`) and assign column aliases (`AS quota_surplus`).
> 6. **`DISTINCT`**: Remove duplicate output rows.
> 7. **`ORDER BY`**: Sort the final rows (can reference `SELECT` aliases!).
> 8. **`LIMIT` / `OFFSET-FETCH` / `TOP`**: Return only the requested page of rows.

```sql
CREATE TABLE sales_reps (
    rep_id INT PRIMARY KEY,
    full_name VARCHAR(50) NOT NULL,
    region_name VARCHAR(30) NOT NULL,
    monthly_quota DECIMAL(10, 2) NOT NULL,
    ytd_sales DECIMAL(10, 2) NOT NULL,
    bonus_pct DECIMAL(4, 2)
);

INSERT INTO sales_reps VALUES

SELECT
    rep_id,
    full_name,
    region_name,
    ytd_sales,
    ROUND(ytd_sales - monthly_quota, 2) AS quota_surplus
FROM sales_reps

```

```sql
SELECT
```

### Key Terminology

1. **Projection (`SELECT` List)**: Choosing which subset of columns and calculated expressions to include in the output table ([SELECT Examples T-SQL](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-examples-transact-sql?view=sql-server-ver17)).
   Syntax: `SELECT rep_id, full_name, ytd_sales FROM sales_reps;`
2. **Logical Query Processing Order**: The conceptual sequence (`FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> DISTINCT -> ORDER BY -> LIMIT/FETCH`) that governs alias visibility and when filters are applied.
   Syntax: `FROM sales_reps WHERE ytd_sales > 40000 GROUP BY region_name`
3. **Covering Index**: A nonclustered/secondary index that contains **all** the columns requested in your `SELECT`, `WHERE`, and `ORDER BY` clauses—allowing the database to answer the query purely from the index without touching the main table pages ([SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)).
   Syntax: `CREATE INDEX idx_reps_region_sales ON sales_reps(region_name, ytd_sales);`
4. **`ONLY_FULL_GROUP_BY` Rule**: Standard ANSI SQL rule (enforced by default in both SQL Server T-SQL and MySQL 8.4) requiring that every column in the `SELECT` list of a grouped query must either appear in the `GROUP BY` clause or be wrapped inside an aggregate function (`SUM`, `COUNT`, `AVG`, `MIN`, `MAX`).
   Syntax: `SELECT region_name, SUM(ytd_sales) FROM sales_reps GROUP BY region_name;`

> [!important] Key Rules to Remember
>
> - **Why `SELECT *` Hurts Performance** → `SELECT *` forces the engine to read every column (including large `TEXT`/`BLOB`/`VARCHAR(MAX)` fields), prevents **Covering Index** optimizations, and can break application code or views if columns are reordered or added later.
> - **`WHERE` vs. `HAVING`** → `WHERE` filters individual rows **before** `GROUP BY` (Step 2); `HAVING` filters aggregated groups **after** `GROUP BY` (Step 4). Never put non-aggregate filters in `HAVING` when they can be filtered early in `WHERE`!
> - **Arithmetic with `NULL` Produces `NULL`** → In `SELECT ytd_sales * bonus_pct`, if `bonus_pct` is `NULL`, the entire expression evaluates to `NULL`. Wrap nullable columns in `COALESCE(bonus_pct, 0.00)`.
> - **Alias Visibility Rule** → A column alias created in `SELECT` (`AS quota_surplus`) is **never** visible in `WHERE` (in any SQL database). It is guaranteed to be visible in `ORDER BY` (Step 7).

## Edge Case Analysis

### 1. Selecting a Non-Grouped Column in a `GROUP BY` Query (`ONLY_FULL_GROUP_BY`)
**Problem:** Writing `SELECT region_name, full_name, SUM(ytd_sales) FROM sales_reps GROUP BY region_name;` fails in SQL Server (`Msg 8120`) and MySQL 8.4 (`Error 1055: incompatible with sql_mode=only_full_group_by`) because the `'South'` region has two different `full_name` values (`'Ananya'` and `'Vikramaditya'`), so the engine does not know which name to display!
**Fix:** Only include `GROUP BY` columns and aggregate functions (`MIN(full_name)`, `MAX(full_name)`, `COUNT(*)`) in the `SELECT` list.

```sql
-- Valid in ANSI SQL, MySQL 8.4, and SQL Server T-SQL
SELECT
    region_name,
    COUNT(full_name) AS reps_in_region,
    MAX(ytd_sales) AS top_rep_sales
FROM sales_reps
GROUP BY region_name;
```

### 2. Using a `SELECT` Alias in `GROUP BY` / `HAVING` (MySQL Extension vs. ANSI/T-SQL Strictness)
**Problem:** MySQL 8.4 leniently allows you to reference a `SELECT` alias inside `GROUP BY` and `HAVING`, but **ANSI SQL and SQL Server (T-SQL) strictly forbid it** because `GROUP BY` (Step 3) and `HAVING` (Step 4) execute *before* `SELECT` (Step 5)!
**Fix:** Always write the underlying column or aggregate expression inside `GROUP BY` and `HAVING` (or wrap the query in a CTE/derived table) so your SQL runs everywhere.

```sql
-- Portable across both SQL Server T-SQL and MySQL 8.4
SELECT
    region_name,
    SUM(ytd_sales) AS regional_sales
FROM sales_reps
GROUP BY region_name
HAVING SUM(ytd_sales) >= 100000.00;
```

### 3. `COUNT(*)` vs. `COUNT(bonus_pct)` in `SELECT`
**Problem:** `COUNT(*)` counts all 5 sales reps, whereas `COUNT(bonus_pct)` ignores `NULL` values and returns `3`!
**Fix:** Use `COUNT(*)` to count total rows and `COUNT(column_name)` specifically when counting non-null occurrences ([Using MIN and MAX / Aggregate Functions](https://apxml.com/courses/sql-for-data-science/chapter-4-aggregating-data/finding-min-max)).

```sql
-- Comparing total rows vs non-null bonus_pct rows
SELECT
    COUNT(*) AS total_reps,
    COUNT(bonus_pct) AS reps_with_bonus,
    COUNT(*) - COUNT(bonus_pct) AS reps_without_bonus
FROM sales_reps;
```

## Going Deeper (Intermediate -> Advanced)

### 1. How Covering Indexes Speed Up `SELECT col1, col2` vs. `SELECT *`

When you create a nonclustered index `CREATE INDEX idx_region_sales ON sales_reps(region_name, ytd_sales);`:
- If you run `SELECT region_name, ytd_sales FROM sales_reps WHERE region_name = 'South';`, the database reads **only** the compact index leaf pages (**Index-Only Scan / Covering Index Seek**).
- If you run `SELECT * FROM sales_reps WHERE region_name = 'South';`, the index does not contain `full_name` or `monthly_quota`, forcing the engine to perform an extra random I/O **Key Lookup / Bookmark Lookup** back into the clustered table for every matching row ([SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17))!

## Interview Corner

### Common Questions & Concise Answers

**Q1: Recite the 8 steps of SQL's Logical Query Execution Order.**  
A: (1) `FROM` / `JOIN`, (2) `WHERE`, (3) `GROUP BY`, (4) `HAVING`, (5) `SELECT`, (6) `DISTINCT`, (7) `ORDER BY`, (8) `LIMIT` / `OFFSET-FETCH` / `TOP`.

**Q2: Why can you use a `SELECT` column alias in `ORDER BY`, but NOT in `WHERE`?**  
A: Because `WHERE` is evaluated at **Step 2** before `SELECT` (Step 5) has defined the column alias, whereas `ORDER BY` is evaluated at **Step 7** after `SELECT` has already projected and named the output columns.

**Q3: Give three concrete reasons why `SELECT *` is discouraged in production queries.**  
A: (1) It defeats **Covering Indexes**, forcing expensive key lookups to fetch unused columns; (2) it wastes disk I/O, buffer pool RAM, and network bandwidth (especially when `TEXT`/`BLOB`/`VARCHAR(MAX)` columns exist); (3) it can break `INSERT INTO ... SELECT` or client positional mappings if table columns are added or reordered.

**Q4: What is the difference between `WHERE` and `HAVING`?**  
A: `WHERE` filters individual table rows at Step 2 *before* `GROUP BY` runs (and cannot contain aggregate functions), whereas `HAVING` filters grouped summary buckets at Step 4 *after* `GROUP BY` runs (using aggregate functions like `HAVING SUM(ytd_sales) > 100000`).

**Q5: What does `SELECT 10 + NULL;` return in SQL, and how do you prevent it?**  
A: Any arithmetic operation involving `NULL` returns `NULL`. Prevent it by replacing `NULL` with a default number using `COALESCE(col, 0)`.

## Warning Block (Best Practice)

> [!warning] Common Mistake (Avoid This!)
>
> ```sql
> -- BAD - Putting non-aggregate row filters in HAVING instead of WHERE, and using SELECT *
> SELECT region_name, SUM(ytd_sales)
> FROM sales_reps
> GROUP BY region_name
> HAVING region_name = 'South'; -- Wastes CPU grouping all regions first before discarding them!
> ```
>
> ```sql
> -- GOOD - Filtering rows early in WHERE (Step 2) before GROUP BY (Step 3)
> SELECT
>     region_name,
>     SUM(ytd_sales) AS total_south_sales
> FROM sales_reps
> WHERE region_name = 'South'
> GROUP BY region_name;
> ```
