# Database Normalization (1NF, 2NF, 3NF) in SQL

#### TL;DR (Quick Revision)

**Database Normalization (`1NF -> 2NF -> 3NF -> BCNF`)** = Splitting bloated tables so every column depends on **the key (`1NF`), the whole key (`2NF`), and nothing but the key (`3NF`)** + Connecting them cleanly with `1:1`, `1:N`, and `M:N` relationships.

> [!abstract] Core Idea
> **Normalization** is the step-by-step process of organizing columns and tables in a relational database to minimize data redundancy and eliminate **Update, Insertion, and Deletion Anomalies** ([Why Combine Data? - ApX Machine Learning](https://apxml.com/courses/sql-for-data-science/chapter-5-combining-data-multiple-tables/why-combine-data)). Alongside your syllabus's **Design Considerations** (Data Types & Precision, Integrity Constraints, and Naming Conventions), normalization ensures each fact is stored in one authoritative table and recombined at query time via [Primary and Foreign Key Constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints?view=sql-server-ver17).

> [!question] Why Use It?
>
> - **Eliminates Update Anomalies**: If `'Apex Retail Pvt Ltd'` moves from Chennai to Hyderabad, you update **1 row** in `customers` instead of hunting down 10,000 historical order rows.
> - **Eliminates Insertion Anomalies**: You can insert a brand-new product (`503: SFP28 Optical Cable`) into `products` immediately—even before any customer places an order for it.
> - **Eliminates Deletion Anomalies**: Deleting a cancelled order from `orders` never accidentally deletes the last copy of a product's price or a customer's address.
> - **Maximizes Buffer Pool & Index Efficiency**: Narrow, properly typed tables pack more rows into every 16KB MySQL InnoDB page ([Using InnoDB Tables](https://dev.mysql.com/doc/refman/8.4/en/using-innodb-tables.html)) or 8KB SQL Server data page ([SQL Server Index Architecture and Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)).

#### Quick Comparison Table

| Normal Form / Concept | Core Rule to Satisfy | What Violation Looks Like | How to Fix It |
| :--- | :--- | :--- | :--- |
| **First Normal Form (`1NF`)** | **Atomic values** in every cell; no repeating column groups (`item1, item2`) or CSV lists; `PRIMARY KEY` defined | `items_csv = '501, 502'` or columns `phone_1, phone_2` | Split each item onto its own row in a child/junction table. |
| **Second Normal Form (`2NF`)** | Must be in `1NF` + **No Partial Dependencies** (no non-key column can depend on only *part* of a composite primary key) | In `order_items(order_id, product_id)`, storing `product_name` (depends only on `product_id`) | Move `product_name` and `unit_list_price` to `products(product_id)`; move `order_date` to `orders(order_id)`. |
| **Third Normal Form (`3NF`)** | Must be in `2NF` + **No Transitive Dependencies** (no non-key column can depend on another non-key column) | In `orders(order_id)`, storing `customer_id` AND `customer_city` (`order_id -> customer_id -> customer_city`) | Move `customer_name` and `customer_city` into `customers(customer_id)`. |
| **Boyce-Codd Normal Form (`BCNF` `[VERIFY]`)** | Stricter `3NF`: for every dependency `X -> Y`, `X` must be a **superkey** | Overlapping composite candidate keys where a non-key column determines part of a key | Split the determinant `X -> Y` into its own lookup table. |
| **Relationships (`1:1`, `1:N`, `M:N`)** | `1:1` (`UNIQUE` FK), `1:N` (Standard `FOREIGN KEY` on child), `M:N` (Composite PK junction table) | Trying to store an `M:N` relationship (Orders <-> Products) without a bridge table | Create `order_items(order_id, product_id)` referencing both `orders` and `products` ([MySQL Foreign Keys](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)). |

## The Learning Concept

### What Problem Does It Solve?

Imagine storing an e-commerce store's orders in a single unnormalized table `orders_flat`:

```sql
-- BAD - Violates 1NF (CSV list), 2NF (Partial Dependency), and 3NF (Transitive Dependency)
CREATE TABLE orders_flat_bad (
    order_id INT,
    product_id INT,
    product_skus_csv VARCHAR(100), -- Violates 1NF: multiple SKUs stuffed in one cell!
    product_name VARCHAR(60),      -- Violates 2NF: depends only on product_id, not (order_id, product_id)!
    customer_id INT,
    customer_city VARCHAR(40),     -- Violates 3NF: depends on customer_id, not order_id!
    PRIMARY KEY (order_id, product_id)
);
```

This single table suffers from all three classic database anomalies: updating a customer's city requires updating hundreds of rows (**Update Anomaly**), you cannot add a new product until someone orders it because `order_id` is part of the `PRIMARY KEY` (**Insertion Anomaly**), and deleting the only order for a product erases the product's name from your database (**Deletion Anomaly**). Here is the clean `3NF` decomposition:

```sql
-- GOOD - Normalized 3NF tables: customers, products, orders, and the M:N order_items bridge table
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(60) NOT NULL,
    customer_city VARCHAR(40) NOT NULL
);

CREATE TABLE products (
    product_id INT PRIMARY KEY,
    sku_code VARCHAR(20) NOT NULL UNIQUE,
    product_name VARCHAR(60) NOT NULL,
    unit_list_price DECIMAL(10, 2) NOT NULL CHECK (unit_list_price >= 0.00)
);
```

### How SQL Implements It

> [!tip] Three Steps to Normalize Any Schema to 3NF
>
> 1. **Step 1 (`1NF` - Atomicity)**: Eliminate comma-separated lists and repeating column groups (`item1`, `item2`), and define a `PRIMARY KEY`.
> 2. **Step 2 (`2NF` - Whole Key)**: Look at any table with a **composite primary key** `(A, B)`. If a column depends only on `A` or only on `B`, move it to `A`'s or `B`'s own table. *(Note: Any `1NF` table with a single-column `PRIMARY KEY` is automatically in `2NF`!)*
> 3. **Step 3 (`3NF` - Nothing But the Key)**: Look at remaining non-key columns. If `NonKey_1 -> NonKey_2` (like `customer_id -> customer_city`), move `NonKey_2` into a table keyed by `NonKey_1`.

#### Full Runnable Example

```sql
-- Step 1: Create 3NF schema (customers, products, orders, and M:N junction table order_items)
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(60) NOT NULL,
    customer_city VARCHAR(40) NOT NULL
);

CREATE TABLE products (
    product_id INT PRIMARY KEY,
    sku_code VARCHAR(20) NOT NULL UNIQUE,
    product_name VARCHAR(60) NOT NULL,
    unit_list_price DECIMAL(10, 2) NOT NULL CHECK (unit_list_price >= 0.00)
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT NOT NULL,
    order_date DATE NOT NULL,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

CREATE TABLE order_items (
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, product_id),
    FOREIGN KEY (order_id) REFERENCES orders(order_id) ON DELETE CASCADE,
    FOREIGN KEY (product_id) REFERENCES products(product_id)
);

-- Step 2: Insert normalized records (Notice Product 503 exists with 0 orders: no Insertion Anomaly!)
INSERT INTO customers VALUES
(1, 'Apex Retail Pvt Ltd', 'Chennai'),
(2, 'Nimbus Cloud Corp', 'Bengaluru');

INSERT INTO products VALUES
(501, 'SKU-SSD-1TB', 'NVMe Enterprise SSD 1TB', 140.00),
(502, 'SKU-RAM-64G', 'ECC DDR5 64GB Module', 210.00),
(503, 'SKU-CAB-OPT', 'SFP28 Optical Cable 3m', 35.00);

INSERT INTO orders VALUES
(1001, 1, '2026-10-05'),
(1002, 2, '2026-10-12');

INSERT INTO order_items VALUES
(1001, 501, 4),
(1001, 502, 2),
(1002, 501, 10);

-- Step 3: Reconstruct the complete invoice view using INNER JOINs
SELECT
    o.order_id,
    o.order_date,
    c.customer_name,
    c.customer_city,
    p.sku_code,
    p.product_name,
    oi.quantity,
    p.unit_list_price,
    ROUND(oi.quantity * p.unit_list_price, 2) AS line_total
FROM orders AS o
INNER JOIN customers AS c
    ON o.customer_id = c.customer_id
INNER JOIN order_items AS oi
    ON o.order_id = oi.order_id
INNER JOIN products AS p
    ON oi.product_id = p.product_id
ORDER BY o.order_id ASC, p.product_id ASC;
```

### Key Terminology

1. **Functional Dependency (`X -> Y`)**: Column `Y` is functionally dependent on column(s) `X` if knowing the value of `X` uniquely determines the value of `Y` (e.g., `product_id -> product_name`).
   Syntax: `product_id INT PRIMARY KEY`
2. **Partial Dependency (Violates `2NF`)**: When a non-key column depends on only **one part** of a composite primary key (e.g., `product_name` depending only on `product_id` inside `order_items(order_id, product_id)`).
   Syntax: Move `product_name` to `products(product_id)`.
3. **Transitive Dependency (Violates `3NF`)**: When a non-key column depends on another non-key column (`order_id -> customer_id -> customer_city`).
   Syntax: Move `customer_city` to `customers(customer_id)`.
4. **Associative / Junction Table (`M:N` Relationship)**: A bridge table (`order_items`) that resolves a Many-to-Many relationship between two parent tables (`orders` and `products`) by holding foreign keys to both parents as a composite `PRIMARY KEY (order_id, product_id)` ([Primary and Foreign Key Constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints?view=sql-server-ver17)).
   Syntax: `PRIMARY KEY (order_id, product_id)`

> [!important] Key Rules to Remember
>
> - **Single-Column PKs Skip Straight from 1NF to 2NF** → If a table is in `1NF` and its `PRIMARY KEY` is a single column (`order_id`), it can never have a partial dependency, so it is **automatically in `2NF`**.
> - **Historical Price Snapshot Is NOT a 2NF Violation** → If `products.unit_list_price` can change over time and you store `unit_price_at_purchase` on `order_items(order_id, product_id)`, that column depends on **both** `product_id` (which item) and `order_id` (when bought), so it is valid `3NF` `[VERIFY]`.
> - **Design Consideration — Precision Sizing** → Size columns to match their real domain (`DECIMAL(10,2)` for prices, `CHAR(2)` for ISO country codes, `SMALLINT` for status codes) rather than declaring `VARCHAR(255)` or `BIGINT` everywhere ([SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)).
> - **Design Consideration — Naming Conventions** → Use consistent lowercase `snake_case` names (`order_items`, `customer_id`), avoid SQL reserved keywords (`order`, `user`, `group`), and name constraints explicitly (`fk_orders_customer`, `uq_products_sku`).

## Edge Case Analysis

### 1. Indexing Foreign Keys in MySQL 8.4 vs. SQL Server (T-SQL)
**Problem:** When you create `FOREIGN KEY (customer_id) REFERENCES customers(customer_id)` on `orders`, **MySQL 8.4 InnoDB automatically creates an index** on `orders(customer_id)` if one does not exist ([MySQL FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)). However, **Microsoft SQL Server does NOT automatically index foreign key columns** ([Primary and Foreign Key Constraints](https://learn.microsoft.com/en-us/sql/relational-databases/tables/primary-and-foreign-key-constraints?view=sql-server-ver17))—causing slow full-table scans on `orders` whenever you join or delete a customer in SQL Server!
**Fix:** Always create an explicit nonclustered index on every foreign key column in SQL Server (and portable DDL scripts).

```sql
-- Explicitly index foreign key columns for fast JOINs and parent DELETE checks in SQL Server & MySQL
CREATE INDEX idx_orders_customer_id ON orders(customer_id);
CREATE INDEX idx_order_items_product_id ON order_items(product_id);
```

### 2. Implementing a True `1:1` Relationship in SQL
**Problem:** How do you enforce that a `user_profiles` table has a strict **One-to-One (`1:1`)** relationship with `users` (rather than `1:N`)?
**Fix:** Make `user_id` in `user_profiles` **both** the `PRIMARY KEY` (or `NOT NULL UNIQUE`) **and** a `FOREIGN KEY` referencing `users(user_id)`.

```sql
-- Enforcing a strict 1:1 relationship between users and user_security_profiles
CREATE TABLE user_security_profiles (
    user_id INT PRIMARY KEY,
    password_hash CHAR(60) NOT NULL,
    mfa_enabled INT NOT NULL DEFAULT 0,
    FOREIGN KEY (user_id) REFERENCES customers(customer_id) ON DELETE CASCADE
);
```

### 3. Composite Primary Key Column Order (`(order_id, product_id)`)
**Problem:** In `order_items`, `PRIMARY KEY (order_id, product_id)` builds a B-Tree sorted first by `order_id`, then by `product_id`. A query filtering only `WHERE product_id = 501` cannot use the primary key's leading column!
**Fix:** Keep the most frequently queried column (`order_id`) first in the composite `PRIMARY KEY`, and add a secondary index on `(product_id)`.

```sql
-- Secondary index supports queries looking up "Which orders contained product_id = 501?"
CREATE INDEX idx_items_product ON order_items(product_id);
```

## Going Deeper (Intermediate -> Advanced)

### 1. Syllabus Row 5: Design Considerations Checklist

Your syllabus highlights three critical **Design Considerations** after normalization:

| Design Consideration | Bad Practice | Production Standard |
| :--- | :--- | :--- |
| **1. Data Types and Precision** | Using `FLOAT` for money or `VARCHAR(4000)` for a 10-character SKU | Use exact `DECIMAL(10,2)` for currency and tight lengths (`VARCHAR(20)`) to keep index keys narrow ([SQL Server Index Design Guide](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-index-design-guide?view=sql-server-ver17)). |
| **2. Integrity Constraints** | Relying solely on frontend JavaScript validation | Enforce `PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL`, `UNIQUE`, and `CHECK` inside the database engine. |
| **3. Naming Conventions** | Mixing `tblOrders`, `Order-ID`, and reserved keyword `Order` | Use lowercase `snake_case` (`orders`, `order_id`, `fk_orders_customer`) for cross-OS portability in MySQL (`lower_case_table_names`) and T-SQL. |

### 2. When Is Denormalization Justified? (`OLTP` vs. `OLAP`)
In transactional **OLTP** databases (order entry, banking), always normalize to `3NF`/`BCNF` so writes are fast and anomaly-free. In analytical **OLAP** data warehouses (Star Schemas in Snowflake, BigQuery, or SQL Server Analysis Services), dimension tables are intentionally denormalized so reporting queries require fewer joins `[VERIFY]`.

## Interview Corner

### Common Questions & Concise Answers

**Q1: Explain `1NF`, `2NF`, and `3NF` in plain English.**  
A: **1NF** requires every cell to hold a single atomic value with no repeating groups and a defined primary key. **2NF** requires `1NF` plus no *partial dependencies* (every non-key column must depend on the entire composite primary key). **3NF** requires `2NF` plus no *transitive dependencies* (no non-key column may depend on another non-key column).

**Q2: Why is any `1NF` table with a single-column `PRIMARY KEY` automatically in `2NF`?**  
A: A partial dependency occurs when a non-key attribute depends on only *part* of a composite key. Because a single-column primary key (`emp_id`) cannot be split into a smaller subset of columns, a partial dependency is mathematically impossible.

**Q3: How do you implement a Many-to-Many (`M:N`) relationship in a relational database?**  
A: You create an **associative (junction/bridge) table** between the two entities (e.g., `order_items` between `orders` and `products`) containing foreign keys referencing each parent's primary key (`order_id` and `product_id`), and declare `PRIMARY KEY (order_id, product_id)`.

**Q4: What is the difference between `3NF` and `BCNF` (Boyce-Codd Normal Form)?**  
A: In `3NF`, a dependency `X -> Y` is allowed if `X` is a superkey *or* if `Y` is a prime attribute (part of some candidate key). In `BCNF`, **every** determinant `X` must be a superkey, eliminating subtle anomalies in tables with multiple overlapping composite candidate keys `[VERIFY]`.

**Q5: What critical difference exists between MySQL 8.4 and SQL Server when you create a `FOREIGN KEY` constraint?**  
A: MySQL 8.4 InnoDB automatically creates a B-Tree index on the referencing foreign key column if one does not exist ([MySQL FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html)), whereas SQL Server does **not** automatically index foreign keys—requiring you to manually run `CREATE INDEX` to prevent table scans on joins and parent deletes.

## Warning Block (Best Practice)

> [!warning] Common Mistake (Avoid This!)
>
> ```sql
> -- BAD - Storing comma-separated foreign keys in a single column (Violates 1NF & breaks JOINs!)
> CREATE TABLE orders_bad (
>     order_id INT PRIMARY KEY,
>     product_ids_csv VARCHAR(255) -- e.g. '501,502,503'
> );
> ```
>
> ```sql
> -- GOOD - Using a normalized M:N junction table with a composite PRIMARY KEY
> CREATE TABLE order_items (
>     order_id INT NOT NULL,
>     product_id INT NOT NULL,
>     quantity INT NOT NULL CHECK (quantity > 0),
>     PRIMARY KEY (order_id, product_id)
> );
> ```
