# Dates & Times

## TL;DR

Adding 14 days to a book's start date should not accidentally erase the original start date. `DateTimeImmutable` lets you store, shift, and format dates with explicit timezones while always returning a fresh object instead of mutating the original.

> [!NOTE] Prerequisites: 22, 31
> New terms: immutable, timezone

> [!abstract] Core Idea
> Use `DateTimeImmutable` with a `DateTimeZone` to represent dates, call `->modify()` to get a new shifted date, and call `->format()` to print it.
> Like Java's `ZonedDateTime` or Python's `datetime`, PHP's `DateTimeImmutable` keeps the original value untouched and returns a brand-new object on every change.

## Mental Model

Think of `DateTimeImmutable` like writing a book's due date on a new sticky note instead of erasing the start date on the original card. Calling `$start->modify('+14 days')` hands you a second sticky note (`$due`) while `$start` stays intact.

```mermaid
flowchart LR
    S["$start = new DateTimeImmutable('2026-11-22')"] -->|"->modify('+14 days')"| D["$due = 2026-12-06<br/>($start stays 2026-11-22)"]
    D -->|"->format('Y-m-d')"| T["'2026-12-06'"]
```

- **Immutable** means an object cannot be changed after creation; methods like `->modify()` return a new copy with the updated value.
- A **timezone** (`DateTimeZone`) defines the local clock offset and daylight-saving rules for a region, such as `'UTC'` or `'Asia/Kolkata'`.

## Minimal Example

```php
<?php
$tz = new DateTimeZone('Asia/Kolkata');
$started = new DateTimeImmutable('2026-11-22 10:00:00', $tz);
$due = $started->modify('+14 days');

echo 'Started: ' . $started->format('Y-m-d') . PHP_EOL;
echo 'Target:  ' . $due->format('Y-m-d') . PHP_EOL;
```

Expected output:

```text
Started: 2026-11-22
Target:  2026-12-06
```

- `new DateTimeZone('Asia/Kolkata')` sets an explicit region **timezone** using the standard `Area/Location` format.
- `new DateTimeImmutable('2026-11-22 10:00:00', $tz)` creates an **immutable** date-time object in that timezone.
- `$started->modify('+14 days')` returns a brand-new `DateTimeImmutable` 14 days later without changing `$started`.
- `->format('Y-m-d')` converts the object into a string (`2026-12-06`).

## Compare

| Class               | Calling `->modify('+14 days')` | Original Variable | Recommended?                           |
| ------------------- | ------------------------------ | ----------------- | -------------------------------------- |
| `DateTimeImmutable` | Returns a new object           | Unchanged         | ✓ Yes (default choice)                 |
| `DateTime`          | Mutates object in place        | Changed too!      | ✗ Avoid unless mutation is intentional |

## ◈ Edge Case Analysis

✗ **Mistake 1:** Using mutable `DateTime` when calculating a due date silently overwrites your original `$started` date as well.

```php
$started = new DateTime('2026-11-22');
$due = $started->modify('+14 days');
echo $started->format('Y-m-d'); // Prints 2026-12-06! Original date is gone
```

✓ **Fix:** Always use `DateTimeImmutable` so `$started` keeps its original date.

```php
$started = new DateTimeImmutable('2026-11-22');
$due = $started->modify('+14 days'); // $started stays 2026-11-22
```

✗ **Mistake 2:** Calling `$started->modify('+14 days');` on `DateTimeImmutable` without saving the return value leaves `$started` unchanged.

```php
$started->modify('+14 days'); // Return value is discarded
echo $started->format('Y-m-d'); // Still 2026-11-22
```

✓ **Fix:** Always assign the returned object to a variable (`$due = $started->modify('+14 days');`).

```php
$due = $started->modify('+14 days');
```

✗ **Mistake 3:** Passing an unknown timezone string to `new DateTimeZone()` throws a `DateInvalidTimeZoneException` (a subclass of `Exception`).

```php
$tz = new DateTimeZone('Mars/City'); // Throws DateInvalidTimeZoneException
```

✓ **Fix:** Use valid IANA timezone names such as `'UTC'`, `'Asia/Kolkata'`, or `'America/New_York'`.

```php
$tz = new DateTimeZone('UTC');
```

## Try It

1. Create a `DateTimeImmutable` for `'2026-01-01'` in `'UTC'`, add `'+1 month'`, and echo it formatted as `'Y-m-d'`.
2. Convert that `'UTC'` date to `'Asia/Kolkata'` using `->setTimezone(new DateTimeZone('Asia/Kolkata'))` and print it with `'Y-m-d H:i P'`.

<details>
<summary>◈ View Solution</summary>

1. Adding one month immutably:

```php
<?php
$start = new DateTimeImmutable('2026-01-01', new DateTimeZone('UTC'));
$next = $start->modify('+1 month');
echo $next->format('Y-m-d') . PHP_EOL; // 2026-02-01
```

2. Converting timezone:

```php
$local = $start->setTimezone(new DateTimeZone('Asia/Kolkata'));
echo $local->format('Y-m-d H:i P') . PHP_EOL; // 2026-01-01 05:30 +05:30
```

</details>

- [ ] A) `$d` becomes `'2026-11-27'`
- [ ] B) `$d` stays `'2026-11-22'` because `modify()` returns a new object instead of changing `$d`
- [ ] C) PHP throws a `TypeError`
- [ ] D) `$d` becomes `null`

- [ ] A) `DateTime` cannot format dates
- [ ] B) `DateTimeImmutable` prevents accidental in-place mutation bugs when passing dates around
- [ ] C) `DateTime` does not support timezones
- [ ] D) `DateTimeImmutable` is the only class with `->modify()`

**Q4: Which format string outputs `'2026-11-22'`?**

- [ ] A) `'YYYY-MM-DD'`
- [ ] B) `'Y-m-d'`
- [ ] C) `'%Y-%m-%d'`
- [ ] D) `'y-M-D'`

**Q5: What happens when you pass `'Invalid/Zone'` to `new DateTimeZone('Invalid/Zone')`?**

- [ ] A) It falls back to `'UTC'` silently
- [ ] B) It returns `null`
- [ ] C) It throws an exception (`DateInvalidTimeZoneException`)
- [ ] D) It uses the browser's timezone

**Q6: Which method converts a `DateTimeImmutable` from `'UTC'` to `'Asia/Kolkata'`?**

- [ ] A) `->changeZone('Asia/Kolkata')`
- [ ] B) `->setTimezone(new DateTimeZone('Asia/Kolkata'))`
- [ ] C) `->format('Asia/Kolkata')`
- [ ] D) `->modify('Asia/Kolkata')`

<details>
<summary>◈ View Answers & Explanations</summary>

1. **B** — `DateTimeImmutable` never modifies the original object (`$a`), so `$a` remains `'2026-11-22'` while `$b` holds `'2026-11-23'`. A describes mutable `DateTime`.
2. **B** — Because `DateTimeImmutable` is **immutable**, `->modify()` creates and returns a new object; discarding that return value leaves `$d` unchanged. A, C, and D are false.
3. **B** — `DateTime` mutates in place, which easily causes subtle bugs if two variables reference the same object. `DateTimeImmutable` avoids that completely. A, C, and D are false.
4. **B** — In PHP's `format()`, `Y` is the 4-digit year, `m` is the zero-padded month, and `d` is the zero-padded day. A, C, and D use non-PHP or wrong format codes.
5. **C** — Passing an unknown timezone identifier to `DateTimeZone` throws a `DateInvalidTimeZoneException` (an `Exception`). It does not fall back to UTC (A) or return `null` (B).
6. **B** — `->setTimezone(new DateTimeZone('...'))` returns a new `DateTimeImmutable` adjusted to the target **timezone**. A, C, and D are invalid.

</details>

## One-Liner

> [!tip] Never Mutate Dates
> **Use `DateTimeImmutable` with an explicit `DateTimeZone`, and always save the new object returned by `->modify()`.**
