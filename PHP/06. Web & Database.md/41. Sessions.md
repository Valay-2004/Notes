# Sessions

## TL;DR

Unlike cookies—where the browser holds and can edit the data—**sessions** keep user data safely on your PHP server. The browser only holds a random **session ID** cookie, and PHP automatically loads that user's `$_SESSION` array on each request.

> [!NOTE] Prerequisites: 38, 40
> New terms: session, session ID

> [!abstract] Core Idea
> Call `session_start()` before any output to read and write server-side user state in `$_SESSION`, and call `session_regenerate_id(true)` after login.
> Like Flask's `session` dictionary, PHP lets you read and write a `$_SESSION` array across requests, except PHP stores the actual data on the server rather than inside the cookie.

## Mental Model

Think of a **session** like a library coat check. You hand your coat (`user_id`, `reading_goal`) to the attendant (the PHP server), and they hand you a numbered claim ticket (the **session ID** cookie). On your next visit, you show only the ticket number, and PHP pulls your coat back out of `$_SESSION`.

```mermaid
flowchart LR
    B["Browser sends PHPSESSID cookie"] -->|"session_start()"| P["PHP finds matching server file"]
    P --> S["Populates $_SESSION array"]
    S -->|"Script ends"| W["Saves $_SESSION back to server"]
```

- A **session** is server-side storage that remembers data for a specific user across multiple HTTP requests.
- A **session ID** is the random token (usually stored in a cookie named `PHPSESSID`) that links a visitor's browser to their server-side `$_SESSION` data.

## Minimal Example

```php
<?php
session_start();

// After verifying a user's login:
session_regenerate_id(true);
$_SESSION['user'] = 'Valay';

echo 'Logged in as ' . htmlspecialchars($_SESSION['user'], ENT_QUOTES, 'UTF-8') . PHP_EOL;
```

- `session_start()` creates a new **session** (or resumes the existing one matching the visitor's **session ID** cookie) and fills `$_SESSION`.
- `session_regenerate_id(true)` issues a brand-new **session ID** and deletes the old session file—essential right after login.
- `$_SESSION['user'] = 'Valay';` saves `'Valay'` on the server so later pages can read `$_SESSION['user']` after calling `session_start()`.

> [!warning] Security angle
> Always call `session_regenerate_id(true)` immediately after a user logs in. This prevents session fixation, where an attacker tricks a user into logging in with a known **session ID**.

## Compare

| Feature                  | Cookie (`$_COOKIE`)      | Session (`$_SESSION`)                    |
| ------------------------ | ------------------------ | ---------------------------------------- |
| Where data is stored     | User's browser           | PHP server                               |
| User can edit data?      | ✓ Yes                    | ✗ No (user only sees the **session ID**) |
| Needs `session_start()`? | ✗ No                     | ✓ Yes, on every page using `$_SESSION`   |
| Best for                 | UI preferences (`theme`) | Logged-in user ID, roles, flash messages |

## ◈ Edge Case Analysis

✗ **Mistake 1:** Reading or writing `$_SESSION` without calling `session_start()` first leaves `$_SESSION` empty or unsaved between requests.

```php
<?php
echo $_SESSION['user'] ?? 'Guest'; // Always 'Guest' if session_start() was skipped!
```

✓ **Fix:** Call `session_start()` at the top of every script that reads or writes `$_SESSION`.

```php
<?php
session_start();
echo $_SESSION['user'] ?? 'Guest';
```

✗ **Mistake 2:** Calling `session_start()` after `echo` or HTML output triggers a _"headers already sent"_ warning when PHP tries to send the `PHPSESSID` cookie.

```php
<p>Welcome</p>
<?php session_start(); // Warning: headers already sent
```

✓ **Fix:** Always place `session_start()` before any HTML, `echo`, or whitespace.

```php
<?php
session_start();
?>
<p>Welcome</p>
```

✗ **Mistake 3:** Calling `session_destroy()` on logout without clearing `$_SESSION = []` leaves the old values in `$_SESSION` for the rest of the current script.

```php
session_destroy();
echo $_SESSION['user']; // Still prints 'Valay' in this request!
```

✓ **Fix:** Reset `$_SESSION = [];` before calling `session_destroy()` when logging a user out.

```php
$_SESSION = [];
session_destroy();
```

## Try It

1. Write a short login script snippet that starts a session, regenerates the **session ID**, and stores `$_SESSION['user_id'] = 42`.
2. Write the two lines needed to log the user out cleanly by clearing `$_SESSION` and destroying the session.

<details>
<summary>◈ View Solution</summary>

1. Starting a session and regenerating ID on login:

```php
<?php
session_start();
session_regenerate_id(true);
$_SESSION['user_id'] = 42;
```

2. Logging out cleanly:

```php
<?php
session_start();
$_SESSION = [];
session_destroy();
```

## Topic Mastery Quiz

**Q1: Where is the actual `$_SESSION` data stored in PHP?**

- [ ] A) Inside the browser's URL query string
- [ ] B) On the PHP server (while the browser only stores the **session ID** cookie)
- [ ] C) Inside `composer.json`
- [ ] D) In the user's `$_GET` array

**Q2: What must you call before reading or writing `$_SESSION` in a PHP script?**

- [ ] A) `setcookie()`
- [ ] B) `session_start()`
- [ ] C) `session_destroy()`
- [ ] D) `header('Session: start')`

**Q3: Why should you call `session_regenerate_id(true)` right after a user logs in?**

- [ ] A) It speeds up JSON encoding
- [ ] B) It replaces the old **session ID** with a fresh one to prevent session fixation attacks
- [ ] C) It deletes `$_SESSION['user']`
- [ ] D) It converts the session into a cookie

**Q4: Why must `session_start()` run before any `echo` or HTML output?**

- [ ] A) `echo` deletes `$_SESSION`
- [ ] B) `session_start()` sends a session cookie in the HTTP headers, which must come before body output
- [ ] C) `session_start()` only works in CLI mode
- [ ] D) HTML clears cookies automatically

**Q5: What happens if you call `session_destroy()` without setting `$_SESSION = []`?**

- [ ] A) `$_SESSION` still holds the old array values for the rest of the current request
- [ ] B) PHP throws a fatal error
- [ ] C) The browser crashes
- [ ] D) `session_start()` stops working forever

**Q6: Which statement best compares cookies and sessions?**

- [ ] A) Cookies are stored on the server; sessions are stored in the browser
- [ ] B) Sessions store data on the server and give the browser only a **session ID**; cookies store data in the browser
- [ ] C) Both store all data inside `$_POST`
- [ ] D) Sessions cannot be used with `$_COOKIE`

<details>
<summary>◈ View Answers & Explanations</summary>

1. **B** — PHP keeps `$_SESSION` data on the server and sends only a random **session ID** cookie (`PHPSESSID`) to the browser. A, C, and D are false.
2. **B** — `session_start()` initializes or resumes the session and populates `$_SESSION`. Without it, `$_SESSION` is not loaded or saved. A, C, and D are wrong.
3. **B** — Regenerating the **session ID** on login prevents an attacker from reusing a pre-login session ID (session fixation). A, C, and D are false.
4. **B** — Cookie-based sessions send an HTTP `Set-Cookie` header when `session_start()` runs, so it must execute before any output begins. A, C, and D are false.
5. **A** — `session_destroy()` removes the stored session data on the server, but it does not unset the in-memory `$_SESSION` array for the current script unless you also run `$_SESSION = []`. B, C, and D are false.
6. **B** — Sessions keep sensitive state on the server behind a **session ID**, whereas cookies store data directly in the browser. A reverses them, and C and D are false.

</details>

## One-Liner > [!tip] Server-Side State > **Call `session_start()` before output, keep secrets in `$_SESSION`, and run `session_regenerate_id(true)` on login.**
